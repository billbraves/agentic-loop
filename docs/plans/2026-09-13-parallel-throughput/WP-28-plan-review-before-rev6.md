## 一、这一轮为什么又返工

rev5 的**两个标的本身兑现了**，codex 的 5 条非阻断结论与我的独立复核逐条一致：

- 撤销 fix 后 M-T0/M-T0b 转红（rev4 同一动作是 `2 passed`）—— 用例终于承重
- oracle 第 4 项判别句与冻结文本逐字节相符，两份模板 sha256 相同
- 零回归算术自洽（`def test_` 全仓 514→514，未增删用例）

阻断项 **B54** 出在**载具本身**，不在标的：`_mutate_on_disk` 的还原保证只覆盖
`yield` 之后的失败。我用交付源码里的 carrier 原文（`exec` 而非重抄）对模板副本实测，
codex 指出的三条全部复现：

| 场景 | 实测 |
|---|---|
| 第二份的 no-op guard 失败 | 第一份留在变异态（写入循环在 `try` 之前，`finally` 从不执行） |
| `finally` 内第一份恢复写入抛错 | 第二份完全不获恢复尝试 |
| 正常路径（控制组） | 两份都恢复 —— 探针有判别力 |

**可达性不是理论的**：`_crlf_rewrap_bytes` 对已是 CRLF 的文件是恒等映射
（实测 CRLF 输入 `changed = False`）。模板一旦以 CRLF 落盘（Windows 检出、
`.gitattributes` 改动、编辑器改行尾），M-T0 会让真实模板留在 CRLF 变异态 ——
而 CRLF 恰好正是这条不变式要抓的那种字节改动。

## 二、根因还是在我这里，且是同一个形状的第二次

rev5 的根因是我 rev4 §A.4 的措辞把变异载具默认成了内存值。
rev6 的根因是：**我把「变异必须落到真实输入面」直接翻译成了「写真实仓库文件」** ——
这两件事并不等价。判据的输入面是「一个文件的字节」，不是「那两个特定路径的文件」。
我在 brief §C 里写了 `try / finally` 与字节还原断言，等于亲手把方案钉在了
「原地改真文件」这条最危险的路上，然后要求执行者把它做安全。

而 rev5 brief §附注 2 就写着「避免一条漏恢复污染另一条」—— 我的复核探针只测了
`yield` 之后的失败，初始化阶段和恢复阶段自身的失败一条都没测。这与
`review-the-dod-not-your-own-concerns` 是同一形状：探针盯着上一轮的缺陷
（读路径承重性），漏掉 brief 里从没人攻击过的那行。

**连续两轮的根因都在计划侧，不在执行侧。** 执行者两轮都精确照做了我写的东西。

## 三、两个修法我都已实测（不把未验证的判据写进 brief）

### 方案 A：按 codex 的五条硬化原地载具

把校验全部前移到落盘之前、写入移入 `try`、`finally` 内逐路径独立尝试恢复
（收集错误而非 inline assert）、全部恢复完再统一校验抛错。

实测（探针 `probe-optionA.py`，只动副本）：

| 场景 | 硬化前 | 硬化后 |
|---|---|---|
| 第二份 guard 失败 | A 未恢复 / B 已恢复 | **两份都恢复** |
| `finally` 内第一份写入抛错 | 两份都未恢复 | A 未恢复（磁盘真写不进去，无法可为）/ **B 已恢复** |
| 用例主体抛异常 | 两份都恢复 | 两份都恢复 |
| 正常路径 | 两份都恢复 | 两份都恢复 |

即 codex 的五条修法有效：第一格由「污染」变「干净」，第二格由「连带失败」变
「只剩真正写不进去的那一个」。**但风险面依旧存在** —— 它仍在写真实模板。

### 方案 B：改变异副本，真实模板一次都不碰

把两份模板 `copyfile` 到临时目录，对副本施加字节变异，判据读副本。

实测（探针 `probe-optionB.py`，直接 import 交付的判据模块）：

| | fix 在场 | fix 撤销 |
|---|---|---|
| M-T0（两侧） | `['SECTION_MISSING']`，`REPLICA_MISMATCH` 不在场 ✅ | `[]` → **用例转红** ✅ |
| M-T0b（单侧） | `['REPLICA_MISMATCH','SECTION_MISSING']` ✅ | `[]` → **用例转红** ✅ |

且 `真实模板 sha256 前后一致 = True`。

**承重性完全保留**：变异仍施加于文件字节，判据仍必须经
`_read_text_preserving_newlines` 才能看见它，撤销 fix 依旧转红。
`_read_text_preserving_newlines(path)` 与 `_check_both(text, text)` 都接受任意路径／文本，
无需改动判据本身。

**B54 的整个失败类在方案 B 下不存在** —— 没有需要还原的东西，
`tempfile` 目录由 OS 与 pytest 负责清理，真实模板不可能被弄脏。

## 四、我的建议：方案 B

理由不是「更省事」，是**风险面消除优于风险面加固**：

1. 这个 carrier 保护的正是「模板受保护块逐字节冻结」。让它去写被保护的文件本身，
   一旦漏还原，脏的方向恰好是判据要抓的那种改动 —— 失效模式与保护目标同向。
2. 方案 A 即使全部硬化，第二格仍留「A 未恢复」（磁盘真写不进去时无法可为）。
   方案 B 把这一格整个删掉。
3. 承重性已实测不受影响 —— 这是唯一不能让的东西，它没让。
4. 「变异必须施加于真实输入面」的规范条目不受影响：副本的字节仍是**文件字节**，
   仍跨读路径。**输入面指的是「一个文件的字节」，不是「那两个特定路径」** ——
   这正是我 rev5 没分清、需要在条目里补一句的地方。

## 五、顺带要修的一处口径

rev5 落成的 oracle 第 4 项现在写着「变异必须施加于判据真实的输入面
（文件字节 / 进程边界 / 外部状态）」。B54 说明这句还差一层：**它没说清「真实输入面」
是否要求写生产制品本身**。我读成了「要」，才把方案钉在原地改真文件上。

建议在该条目补一句判别式说明，明确「同类输入面的等价载体（如临时副本）满足要求；
若变异会写到被判据保护的制品本身，须优先选用不写该制品的等价载体」。

这一句是从 B54 提炼的、可机械检查的规范，与 rev5 折进 B53 判别句的做法同型。
**但它会让 rev6 的范围从「只修载具」扩到「再动一次模板条目」**，所以列为可选项，
由你定 —— 见下方方向 2 与方向 3 的差别。
