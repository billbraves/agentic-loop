## 3.5 外部参考：Hanako「Loops and Graphs」对本项目计划的影响

来源：https://x.com/hanakoxbt/status/2091515787366306154
（2026-08-23，长文标题 *Loops and Graphs: how to stop babysitting agents and
only approve the last step*）。核心框架：**loop 活在 node 内部**
（produce → check → correct → repeat until green），**graph 活在 node 之间**
（splitter / worker / code node / gate + 两条回边）。

### 三条确实有用、且本项目当前没有的

**(1) 门禁按 blast radius 分道，而不是一刀切**
原文：「Confidence is the weakest input... it is the only one the model can
influence. The strong variable is what happens if the change is wrong.」
分三道：可逆且局限 / 可逆但面广 / 不可逆（**这一道不开，与分数无关**）。

对本项目的直接意义：当前**所有 WP 走同一套双签**。WP-24 只改一个测试文件，
与 WP-22 重写 `finalize_merge.sh` 的传输协议，走的是同一道 codex 第二签名。
前者的错误成本是一次 revert，后者是合并门被绕过。
`risk` 块里已经有 `production_writes` / `network` / `data_access` 这套词汇，
但它只用来**声明**约束，从不用来**调节门禁强度**。
→ 建议在阶段 B 增一个 WP：把 blast radius 做成 `scope` 或 `risk` 的派生量，
按道次决定「需不需要第二签名」「需不需要用户批准」。
注意原文的关键区分：不可逆那一道是**一条不开的道**，不是一个设得很高的阈值——
阈值会被调，关闭的道不会。

**(2) 学习回边要机械化，不能停在「文档里记了」**
原文：「The learning edge does not carry the output, it carries a constraint
derived from it... Not in the worker's instructions, in the brief that shapes
how the work gets cut.」以及「any failure you do not turn into a permanent
constraint, you will meet again.」

本项目**已经独立发现了这条边**：WP-24 把 oracle 三项写进 WP 模板、
WP-25 要把四条纪律写进 `CLAUDE.md.tmpl`，都是「把一次失败变成常驻约束」。
但落点只到「模板文本」，**推导仍靠人**：我读 `WP-08-candidate.md` 里
48 条缺陷登记，手写进下一份 brief。缺陷登记本身没有任何机制把自己送进 splitter。
→ 建议：`dispatch_lint` 增一条检查——新 brief 的 DoD 是否覆盖了
登记表里与其 `allowed_paths` 相交的既有缺陷。这是把长回边接到派发面上，
而不是接到我的记忆上。

**(3) 返工次数是「计划有问题」的信号，不是「执行者不行」的信号**
原文：「Cap it at three attempts. If a unit fails three corrections the problem
is in the plan that produced it, and the loop cannot see the plan.」

WP-19 走到了 **rev6**。复盘：多数 rev 不是执行者做错，是我的 brief 判据写错
（rev5 的用例锁了实现路径而非契约，3.14 上失败 = A30）。
按原文的判据，第 3 次返工时就该停下来重看计划，而不是继续改 brief。
→ 建议写进协议：同一 WP 第 3 次 re-freeze 时强制停手，
先复核「是判据错了还是实现错了」，并把结论落进缺陷登记。

### 两条本项目已经独立走到、且比原文更强的

- **门禁先于一切**。原文「Build the gate first... a graph without a gate is
  just a faster way to produce unverified output.」——本仓的存在理由就是这句。
- **不采信模型自评**。原文把 model's own assessment 排在证据序列最后；
  本项目更彻底：A11 已判定 git author 是**提交者可自由声明的字段**，
  不得作为独立性事实，WP-17 因此整个废弃。原文只是「排在最后」，
  这里是「不进判据」。

### 一条原文没覆盖、恰是本项目最贵的教训

原文的 check 只要求「能失败」。本轮四个缺陷（B11/B14/B16/B17）全部是
**check 本身能失败、但读的是错的东西**：抄出来的判据副本、冻结的 CLI 副本、
工作树里的历史快照、按固定命名找错的 brief。B19 更进一步——
一个变异让用例转红了，红却来自外层守卫，不是想钉的那一层。

所以在原文的「produce → check → correct」之外，本项目要多一层：
**check 必须证明自己读的是权威源本体**。这正是 WP-25 三条纪律的内容，
也是它值得优先恢复的理由。原文的框架可以直接采纳，但不能替代这一层。

### 不采纳的部分

原文的 splitter / 并行 / code node 那几条，本项目当前规模用不上：
WP 拆分是我手工做的，一轮 3 个并行已经是上限（本轮 WP-25/26/27 并行派发，
且 26→27 的真边 `preflight.sh:93 → dispatch_lint.sh` 已识别并排了合入顺序，
符合原文「does the next step actually read the previous step\'s output?」的检验）。
瓶颈在配额与判据正确性，不在图的形状。
